# 장애 대응: 앱이 갑자기 종료됐는데 메모리는 여유롭다?

> Velog 원문: https://velog.io/@hyeonminee/%EC%9E%A5%EC%95%A0-%EB%8C%80%EC%9D%91-%EC%95%B1%EC%9D%B4-%EA%B0%91%EC%9E%90%EA%B8%B0-%EC%A2%85%EB%A3%8C%EB%90%90%EB%8A%94%EB%8D%B0-%EB%A9%94%EB%AA%A8%EB%A6%AC%EB%8A%94-%EC%97%AC%EC%9C%A0%EB%A1%AD%EB%8B%A4

- 작성일: Thu, 22 Oct 2026 14:52:05 GMT

---

<p><strong>상황</strong>
클라우드 VM의 웹 앱이 갑자기 종료됐다. 관리자가 접속해 확인하니 메모리에는 여유가 있다.</p>
<pre><code>$ systemctl status myapp

Active: failed
Main process exited, code=killed, status=9/KILL</code></pre><pre><code>$ free -h

               total    used    free    available
Mem:           2.0Gi   0.6Gi   1.2Gi       1.3Gi</code></pre><p>장애 시각의 커널 로그에서는 다음 기록을 찾았다.</p>
<pre><code>Out of memory: Killed process 2841 (java)</code></pre><p><strong>문제</strong></p>
<ol>
<li>현재 메모리에 여유가 있어도 메모리 부족으로 앱이 종료됐다고 판단할 수 있을까? status=9/KILL만으로도 같은 결론을 내릴 수 있을까?</li>
<li>바로 재시작하기 전에 무엇을 확인하고, 복구 후에는 무엇을 검증해야 할까?</li>
</ol>
<hr />
<p><strong>풀이</strong></p>
<ol>
<li><p>커널 로그가 메모리 부족에 따른 종료를 뒷받침한다.
메모리가 부족해 커널이 Java 프로세스를 종료했고, 그 프로세스가 사용하던 메모리가 반환돼 지금은 여유가 생겼을 수 있다. 현재 상태와 장애 당시 상태는 다르다.
다만 status=9/KILL은 강제 종료 신호인 SIGKILL을 받았다는 뜻일 뿐이다. 관리자의 강제 종료 등으로도 발생하므로, 이것만으로 메모리 부족을 확정하면 안 된다.</p>
</li>
<li><p>장애 기록과 자원 상태를 확인한 뒤 복구한다.
다음은 조회용 명령이다. 시간 범위는 실제 장애 시각에 맞춘다.</p>
<pre><code>sudo journalctl -k --since &quot;30 minutes ago&quot; --no-pager
sudo journalctl -u myapp --since &quot;30 minutes ago&quot; --no-pager
free -h
ps -eo pid,comm,rss --sort=-rss | head</code></pre></li>
</ol>
<ul>
<li>journalctl -k: 커널 로그에서 OOM 관련 기록 확인</li>
<li>journalctl -u myapp: 앱의 종료 전후 로그 확인</li>
<li>free -h: 현재 메모리와 스왑 상태 확인</li>
<li>ps ... rss: 현재 프로세스별 실제 메모리 사용량 확인. 여기서 RSS 단위는 KiB다.
모니터링 기록이 있다면 장애 직전의 메모리 사용량, 요청량, 다른 작업 실행 여부도 비교한다. 커널이 Java를 종료했다는 사실만으로 Java의 메모리 누수까지 확정할 수는 없다.
재시작에 필요한 메모리가 확보됐고 충돌하는 작업이 없는지 확인한 뒤 실행한다.
sudo systemctl start myapp
systemctl is-active myapp
curl --max-time 5 -I <a href="http://localhost:8080">http://localhost:8080</a></li>
</ul>
<p>앱 상태와 실제 응답을 확인하고, 이후 메모리 사용량과 오류율이 다시 증가하는지 관찰한다.</p>
<p>핵심 개념</p>
<ul>
<li>OOM(Out Of Memory): 사용할 메모리가 부족한 상태</li>
<li>OOM Killer: 메모리 부족 상황에서 커널이 프로세스를 선택해 종료하는 기능</li>
<li>SIGKILL: 프로세스가 정상 종료 처리를 할 기회 없이 종료되는 신호</li>
<li>시계열 지표: 시간에 따른 자원 변화 기록. 장애 후의 한 번 조회보다 원인 분석에 유용하다.</li>
</ul>
<p><strong>실무에서 중요한 이유</strong>
종료된 앱의 메모리가 반환되면 장애 흔적이 현재 지표에서 사라질 수 있다. 로그와 과거 지표를 함께 봐야 반복 재시작으로 끝나는 대응을 피할 수 있다.
실행 전 점검: 재시작 시 배치 작업·메시지 처리가 중복 실행될 가능성을 확인한다. JVM 힙 크기를 늘릴 때는 운영체제와 다른 프로세스, JVM의 힙 외 메모리도 고려해야 한다. 원인 분석에 필요한 로그를 먼저 확보하고 복구를 진행한다.</p>
