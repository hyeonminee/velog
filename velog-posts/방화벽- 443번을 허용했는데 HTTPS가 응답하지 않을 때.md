# 방화벽: 443번을 허용했는데 HTTPS가 응답하지 않을 때

> Velog 원문: https://velog.io/@hyeonminee/%EB%B0%A9%ED%99%94%EB%B2%BD-443%EB%B2%88%EC%9D%84-%ED%97%88%EC%9A%A9%ED%96%88%EB%8A%94%EB%8D%B0-HTTPS%EA%B0%80-%EC%9D%91%EB%8B%B5%ED%95%98%EC%A7%80-%EC%95%8A%EC%9D%84-%EB%95%8C

<p><strong>상황</strong></p>
<p>클라우드 VM에서 HTTPS 서비스가 TCP 443번 포트로 정상 실행 중이다. 보안 그룹과 네트워크 ACL 설정은 다음과 같다.</p>
<pre><code>보안 그룹

Inbound : TCP 443 허용
Outbound: 전체 허용</code></pre><pre><code>네트워크 ACL

Inbound
100  ALLOW  TCP 443         Source 0.0.0.0/0
*    DENY   ALL

Outbound
100  ALLOW  TCP 443         Destination 0.0.0.0/0
*    DENY   ALL</code></pre><p>외부 클라이언트가 접속할 때의 포트는 다음과 같다.</p>
<pre><code>요청: 클라이언트 53000번 → 서버 443번
응답: 서버 443번 → 클라이언트 53000번</code></pre><p><strong>문제</strong></p>
<ol>
<li>들어오는 443번 통신을 허용했는데도 HTTPS 요청이 시간 초과되는 가장 유력한 이유는 무엇일까?</li>
<li>보안 그룹과 네트워크 ACL의 상태 추적 방식은 어떻게 다르며, 어떤 규칙을 추가해야 할까?</li>
</ol>
<p><strong>풀이</strong>
네트워크 ACL의 <strong>아웃바운드 규칙이 응답 패킷을 차단</strong>하고 있다.</p>
<p>클라이언트는 임시 포트인 53000번을 출발지 포트로 사용한다. 서버의 응답 패킷은 목적지 포트가 443번이 아니라 <strong>53000번</strong>이다. 현재 아웃바운드 ACL은 목적지 443번만 허용하므로 응답이 외부로 나가지 못한다.</p>
<p>네트워크 ACL은 상태를 기억하지 않는 <strong>비상태 저장 방식</strong>이다. 따라서 요청과 응답 방향을 각각 허용해야 한다. 예를 들어 클라이언트의 임시 포트 범위에 대한 아웃바운드 허용 규칙이 필요하다.</p>
<pre><code>Outbound
100  ALLOW  TCP 1024-65535  Destination 필요한 클라이언트 대역
*    DENY   ALL
</code></pre><p>실제 환경에서는 운영체제와 접속 구조에서 사용하는 임시 포트 범위를 확인해 필요한 범위만 허용한다. 변경 전에는 다음 항목을 확인한다.</p>
<pre><code>서비스 수신 포트
→ 보안 그룹
→ 서브넷에 연결된 ACL
→ 인바운드 규칙
→ 아웃바운드 응답 포트
→ 규칙 번호와 우선순위</code></pre><p>네트워크 ACL은 일반적으로 낮은 규칙 번호부터 평가하므로, 허용 규칙보다 앞에 일치하는 차단 규칙이 있는지도 확인해야 한다.</p>

<p>임시 포트는 클라이언트가 서버에 연결할 때 잠시 사용하는 출발지 포트다. 서버의 응답은 이 포트를 목적지로 돌아간다.</p>
<p><strong>실무에서 중요한 이유</strong></p>
<p>클라우드 통신은 서버 방화벽만 통과한다고 끝나지 않는다. 보안 그룹은 정상이어도 서브넷 ACL에서 응답 경로가 차단되면 연결 시간 초과가 발생한다. 이때 애플리케이션이나 443번 인바운드 규칙만 반복해서 확인하면 원인을 찾기 어렵다.</p>
<p>ACL을 변경하기 전에는 대상 서브넷과 연결된 다른 서비스, 기존 규칙 번호, 필요한 클라이언트 주소 범위를 확인한다. <code>0.0.0.0/0</code>에 전체 포트를 허용하면 문제는 사라질 수 있지만 불필요한 노출이 커지므로, 통신 흐름을 기준으로 필요한 방향·포트·주소만 허용해야 한다.</p>
