<p>별도의 트랜잭션 로그 백업이나 복제본은 없다고 가정한다.</p>
<p><strong>문제</strong></p>
<ol>
<li>오전 10시 장애에서 손실될 수 있는 데이터는 몇 시간 분량인가? 현재 구성과 훈련 결과는 RPO·RTO 목표를 각각 만족하는가?</li>
<li>백업 작업에는 매번 <code>성공</code>이 표시된다. 그래도 어떤 점검과 개선이 필요할까?</li>
</ol>
<p><strong>풀이</strong></p>
<ol>
<li><p>최대 4시간 분량의 데이터가 손실될 수 있고, 두 목표 모두 만족하지 못한다.</p>
<ul>
<li><p>RPO: 10시에서 최신 복구 시점인 06시를 빼면 4시간이다. 허용한 1시간을 초과한다.</p>
</li>
<li><p>RTO: 복구 훈련에 90분이 걸렸다. 목표인 60분을 초과한다.</p>
<p>RPO는 “데이터를 언제 시점까지 되돌릴 수 있는가”, RTO는 <strong>“서비스를 얼마나 빨리 다시 사용할 수 있는가”</strong>의 기준이다.</p>
</li>
</ul>
</li>
<li><p>실제 복원 가능성과 복구 시간을 따로 검증한다.
권장 점검 순서는 다음과 같다.</p>
<ol>
<li>복구 시점 확인: 백업 성공 여부뿐 아니라 가장 최근에 복구할 수 있는 시각을 확인한다.</li>
<li>격리된 환경에 복원: 운영 DB를 덮어쓰지 않고 별도의 VM이나 DB에 복원한다.</li>
<li>데이터·서비스 검증: 최근 주문, 데이터 정합성, 앱의 DB 연결과 조회 기능을 확인한다.</li>
<li>전체 소요 시간 측정: 장애 인지부터 인프라 준비, 복원, 연결 변경, 서비스 검증까지 기록한다.</li>
</ol>
</li>
</ol>

<p>백업 간격만 줄여도 복원 시간이 자동으로 짧아지는 것은 아니다. 변경 후 복구 훈련으로 두 목표를 다시 확인해야 한다.</p>
<p><strong>핵심 개념</strong></p>
<ul>
<li>RPO: 허용 가능한 데이터 손실 시간</li>
<li>RTO: 허용 가능한 서비스 중단 시간</li>
<li>시점 복구: 백업과 DB 변경 로그를 이용해 특정 시각의 상태로 복원하는 기능</li>
<li>복구 검증: 파일이 복원됐는지를 넘어 실제 서비스가 정상 동작하는지 확인하는 과정</li>
</ul>
<p><strong>실무에서 중요한 이유</strong>
백업 성공 알림만으로는 데이터 손실 범위나 서비스 복구 시간을 알 수 없다. 주문 서비스에서는 몇 시간의 데이터 손실이 결제·재고 불일치로 이어질 수 있어, 업무 기준에 맞춘 복구 목표와 반복 훈련이 필요하다.</p>
<p><strong>실행 전 점검</strong>: 복원 대상의 계정·리전·DB 이름을 확인하고, 운영 데이터 덮어쓰기를 방지한다. 복원한 앱이 실제 결제·이메일을 실행하지 않도록 외부 연동도 차단한다. 훈련용 자원에는 운영 데이터와 같은 접근 통제를 적용하고 비용도 확인한다.</p>
